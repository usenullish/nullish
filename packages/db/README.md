# db

Database connection, migrations, user contexts and statement helpers.

## Migrations

The migrations live in `migrations/` and run in order. A lot of business rules are enforced by the database itself, with triggers and constraints, and are listed below.

### Adding a migration

A schema change (Drizzle tables, views) is generated with `bun run db:generate`.

Anything else is a custom migration, created with `bunx drizzle-kit generate --custom --name=<type>_<name>`. It comes with:

1. **Its SQL**, written in the generated `migration.sql`.
2. **A comment** at the top of that SQL, which details the rule and why it exists.
3. **A row** in the [list](#list) below: the migration, its change, its domain, its type and a short description.
4. **Tests** in `tests/migrations/rules`, one file per rule, covering what it allows and what it rejects.

A released migration is never edited. Changing a rule is a new migration (e.g. `CREATE OR REPLACE FUNCTION`, `CREATE OR REPLACE TRIGGER`), with the same four parts.

### Types

The name of a migration starts with its type:

| Type         | Contains                                               |
| ------------ | ------------------------------------------------------ |
| `setup`      | One-time initialization (e.g. an extension)            |
| `schema`     | The schema generated by Drizzle, and what completes it |
| `permission` | Grants and role memberships                            |
| `rule`       | Constraints or generated columns, without trigger      |
| `trigger`    | A function and the trigger that runs it                |
| `function`   | A function called directly in SQL                      |
| `seed`       | Data population                                        |
